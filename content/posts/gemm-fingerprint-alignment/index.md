> **TL;DR**：跨硬件（GPU A100 vs NPU 910B2）性能对比，两份分析报告给出 0.60x / 0.31x 的倍数。然后有人数了一遍两侧**每步真实 GEMM 调用次数**：LLaMA(小) 73 vs 29，LLaVA 225 vs 79——**两侧跑的根本不是同一个模型**（层数差一倍/差近三倍），所有跨侧倍数作废。
> 1. **GEMM 调用数/step 是与后端无关的硬指纹**：矩阵乘是逻辑算子，融合策略、kernel 切分都动不了它的次数——数它就能判定"是不是同一个模型、同一份输入"。
> 2. 偏差拖到事后才暴露的根子不在参数层，在**元数据层**：n_params、层数、seq_len 两侧都没记录，已有的 dtype 字段还在说谎。
> 3. 解法是把对齐从"事后考古"变成"事前断言"：四条验收断言 + 16 个单元的目标指纹表 + **先小样对指纹、再跑全量**的返工纪律。修完：57/57、113/113、339/339 精确命中。

## 一切从一个可疑的倍数开始

背景是常规操作：同一批模型在 GPU 和 NPU 上各采一份 eager/compile × inference/train 数据，出对比报告。报告里跨侧倍数看着不大——0.60x、0.31x，NPU 慢一些但没慢到离谱，配上一堆逐算子分析，结论区照常排优先级。

转折是有人对着 kernel 明细数了一遍**每步真实 GEMM 调用次数**（剔除 split-K 归约、gemv 这类伪 GEMM 后）：

| 模型 | GPU GEMM/step | NPU GEMM/step | 倍差 |
|---|---|---|---|
| LLaMA(小) | **73** | **29** | 2.5x |
| LLaVA | **225** | **79** | 2.8x |
| nanoGPT | 48~49 | 49 | 一致 |
| LLaMA-v2-7B | 113 / 339 | 113 / 339 | 一致 |

矩阵乘是逻辑算子：不管后端怎么融合、怎么切分、叫什么名字，**该做的矩阵乘一次都少不了**。次数差 2.5 倍，只剩一种解释——**模型本体不同**。

事后核算（方法见下节）：LLaMA(小) GPU 侧 8 层、NPU 侧 4 层；LLaVA GPU 侧 32 层完整 Llama-7B 语言模型、NPU 侧 12 层。**不是 NPU 快，是 NPU 跑的模型更小。** 两份报告里所有跨侧倍数作废，基于倍数排的优先级一并作废。

## 硬指纹：为什么是 GEMM 数

跨栈对比需要一个不随实现漂移的锚点。候选者和它们的失败原因：

| 候选指纹 | 为什么不可靠 |
|---|---|
| kernel 名 | 融合器把算子揉进 `triton_fused_*`，同名不同义 |
| kernel 数量 | 融合粒度两侧天然不同——这正是被测量的对象 |
| 注意力次数 | 只在两侧都用融合注意力时才可比（一侧手写 softmax 路径时，"0 次"不代表没有注意力） |
| 归一化次数 | 可用，但写法有三种（layer_norm/rsqrt/ReduceMean），要取最大值兜底 |
| **真实 GEMM 数/step** | **逻辑算子，后端动不了次数**（注意剔除 splitKReduce/gemv 伪 GEMM） |

GEMM 数也不是完美的——厂商库会把一个大 GEMM 拆成 split-K（GPU 侧每步多出 24 次 `splitKReduce`），所以口径必须定义为"**真实矩阵乘次数**"：按 kernel 名过滤掉归约尾巴和向量乘。过滤后，它是全部候选里最稳的一个。

实际操作里 GEMM 数 + 归一化实例数 + 参数量算术**三路互证**，比单靠任何一路都硬。

## 法医式定位：从指纹倒推偏差

以 LLaMA(小) 为例，看怎么从两个数字倒推出"层数差一倍"：

```text
GPU 侧：73 GEMM/step = 57（8 层 × 7 + lm_head） + 16（8 层 × 2 次未融合注意力 bmm）
        归一化 17/step = 2 × 8 + 1
NPU 侧：29 GEMM/step = 28（4 层 × 7 + 1）
        归一化 9/step  = 2 × 4 + 1

参数量算术：embed 32000×512 + lm_head 同量 + 8 层 × 3.41M ≈ 60.04M ✓（与 GPU 的
60,039,680 精确一致）；若是 4 层，只有约 46.3M ✗
```

三路证据全部指向同一个结论：GPU 8 层、NPU 4 层，两侧数字各自自洽——**差值不是实现差异，是层数差一倍**。顺带一个小陷阱：GPU 侧那 16 次"多出来"的 GEMM 是未融合注意力的 QK^T 和 AV 矩阵乘，修复方向不是让 NPU 对齐 73，而是**两侧都走融合注意力后对齐 57**——把"要测的形态"和"顺便暴露的实现差异"分开。

LLaVA 的案子多一层：NPU 侧 kernel 里有 **Conv2D、Cumsum、Index**（视觉塔的 patch embed 和图像 token 拼装），GPU 侧一个卷积 kernel 都没有——GPU 根本没喂图像。这已经不是"同一个模型跑得快慢不同"，而是**跑的图不一样**。对策是定死输入契约：要么两侧都不传 `pixel_values`，要么两侧都传同一张图并记录尺寸。

## 为什么拖到现在才发现：会说谎的 meta

复盘偏差为何能潜伏这么久，答案分三层：

| 层 | 典型偏差 | 能否靠改参数修好 |
|---|---|---|
| 参数层 | dtype、warmup/active/repeat、optimizer 口径 | 能（前一轮已修） |
| 模型层 | 层数、hidden、视觉塔是否参与、注意力是否融合 | **不能** |
| 元数据层 | 两侧都不记录 n_params / 层数 / seq_len | **不能** |

参数层的问题早就修完了，剩下的全卡在后两层——而它们能潜伏的直接原因是**元数据缺失**：

- `n_params`、`num_hidden_layers`、`seq_len`：**两侧都没记录**。模型是不是同一个，只能事后从 kernel 名反推。
- 已有的 `dtype` 字段还在**说谎**：GPU 侧 meta 全部声明 float32，实测呢？LLaMA-v2-7B 的 eval 是 **fp16**（权重 f16[32000,4096] 直接可见），LLaVA 的 train 是 **bf16**（kernel 名 `bf16` gemm）。判据是真实 GEMM kernel 名（`ampere_sgemm`=fp32、`ampere_fp16_s16816gemm`=fp16），不采信声明。
- `batch_size`：GPU eval 实际 batch 32，NPU 跑 batch 1——**NPU 只跑了 1/32 的 token 量**，这个也只在 kernel 形状里能看出来。

还有一类隐蔽坑：**同一个模型 eval 和 train 的输入都不同**——LLaMA-v2-7B eval seq 512、train seq 128，两份数据不可互换；"让 NPU 对齐 GPU"这句话本身是歧义的，必须先定死每个单元用哪个 dtype、哪个 seq、哪个 batch。

结论：**meta 不全 + meta 说谎，对齐就只能靠事后考古；而考古是有截止日期的——数据已经采完、报告已经发出去了。**

## 把对齐变成断言：四条验收 + 目标指纹

修复的思路不是"下次仔细点"，是把"对齐"定义成可执行判定——四条断言，全部满足才算一个单元对齐：

| # | 断言 | 判据 | 容差 |
|---|---|---|---|
| A1 | 同一个模型 | n_params 完全相等 + 层数相等 + 权重 sha256 相等 | **0** |
| A2 | 同一份输入 | batch、seq_len、mask 语义、是否传图像全部一致 | **0** |
| A3 | 结构指纹一致 | 真实 GEMM 数/step、归一化实例数/step | ±2 |
| A4 | 口径一致 | warmup/active/repeat、optimizer 有无、驱动 dtype | **0** |

注意容差的语义：**模型和输入零容忍**（差一点都不算同一个实验），结构指纹给 ±2（融合策略可能让边界算子差一两次），口径零容忍。**前两条不满足时，后面的时间对比一律不成立**——这条优先级要写死在工具里，不靠人记。

16 个单元各写一行目标指纹（示例）：

```text
LLaMA-v2-7B compile·eval : GEMM 113±2 / attn 16 / ln 33±1 / fp16 / seq 512
LLaMA-v2-7B compile·train: GEMM 339±2 / attn 32 / ln 33±1 / fp32 / seq 128
LLaMA(小)   compile·eval : GEMM  57±2 / attn  8 / ln 17±1 / fp32 / batch 32（融合注意力后）
LLaVA        compile·eval : GEMM 225±2 / attn 32 / ln 65±1 / fp16 / pixel_values=None
```

配一个自检脚本：输入模型目录，打印各指纹与目标的差，PASS/FAIL。**A1/A2 靠 meta 断言，A3/A4 靠 kernel 明细断言**——meta 补齐字段（n_params、层数、seq、batch、dtype 分参数/激活两列、optimizer 配置、图像契约、真实计时步数），对齐判定就从"老手看 kernel 名猜"变成"脚本跑一遍"。

## 同样重要：不该对齐的五个维度

对齐做过头和不到位一样有害。五个明确**放弃对齐**的维度，以及各自的处理口径：

1. **GEMM 下沉与切分**：cuBLAS split-K vs CANN MatMulV2，切分策略是实现细节 → 只比真实矩阵乘次数；
2. **融合粒度和 kernel 名**：这正是被测量的对象 → 只要求"逻辑算子序列"一致；
3. **主机侧提交路径**：不同 runtime → 只比每次 launch 总成本；
4. **CUDA Graph 类机制**：一侧没有对应物 → 两侧都关闭，不纳入；
5. **样本数与统计量**：一侧只有 2~3 个样本 → 差距 <10% 记"持平"，不硬算显著性。

原则一句话：**对齐"实验设计"层（模型/输入/口径），放过"实现"层**——实现差异正是实验要测的东西。

## 返工纪律：先小样，再全量

修配置的顺序也值得固化。**不要改完配置直接跑全量**——全量跑完才发现层数不对，代价就是一整轮：

```text
① 改配置（~10 分钟）：层数/batch/seq/dtype/图像契约定死，meta 补齐
② 跑 1 step 小样（~3 分钟/模型）：warmup 1 + active 1，出 meta + kernel 明细
③ 自检：check_align 打印指纹差 —— PASS 才继续
④ 跑全量；交付物里附 align_report
```

③ 那一步 3 分钟，换来的是"绝不用一整轮时间验证一个配置错误"。

## 结果与沉淀

按这套流程重采后，结构指纹全部命中：**57/57、113/113 + 339/339 精确相等**（eval 与 train 的 seq 差异也按断言分别锁死）。基于干净口径的四模型对比是另一个故事（加速比演进与"反超 GPU"的收官判定），下篇展开。

这次的方法论压缩成四条：

1. **跨硬件对比，第一件事是数 GEMM**。真实矩阵乘次数/step 是后端无关的硬指纹——数字对不上，后面全是废话。
2. **指纹要三路互证**：GEMM 数 + 归一化实例数 + 参数量算术，单路都可能被实现细节骗到。
3. **meta 是对齐的基础设施，不是附录**。n_params/层数/seq/batch/dtype（分参数与激活）/optimizer/图像契约——字段不全，对齐永远是事后考古；声明字段还要和 kernel 名交叉验证，因为 meta 会说谎。
4. **断言容差分级**：模型/输入/口径零容忍，结构指纹 ±2，不可对齐维度显式声明放弃——"对齐"必须是一份可执行的规格，而不是一句口号。
