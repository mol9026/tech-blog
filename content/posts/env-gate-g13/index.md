> **TL;DR**：环境重建 + 版本升级后，原有的精度门禁（1 层小模型 compile 对比 eager，cos > 0.999 即过）全绿放行。三天后发现这个环境带着三类缺陷：
> 1. **≥3 层 Transformer 整图编译精度崩坏**（cos 0.82，1 层永远测不出来）；
> 2. **reduction 融合 kernel 约 10 倍性能退化**（原门禁根本不测 kernel 计时）；
> 3. **select_algorithm 签名漂移**——只有清空编译缓存后才触发，而门禁跑在热缓存上。
>
> 三类全部静默通过门禁，期间采集的性能数据全部作废。复盘产物是新一代环境门禁（下称 g13）：3 分钟、5 项检查，专抓"1 层 gate 漏检"的静默劣化。

## 事件：三天，一次全绿，一屋子坏数据

事情从一次再寻常不过的环境操作开始：升级 CANN、重装 torch_npu（自编译构建），跑一遍既有的 g12 门禁——1 层小模型 compile vs eager，cos 0.999999，PASS，放行。

接下来三天按正常节奏采性能数据。第三天，一批反常的性能数字（LN 融合 kernel 慢 10 倍量级）触发深查，最终在另一台机器、另一套构建上交叉验证确认（[详见前文](https://mol9026.github.io/tech-blog/posts/cann92-triton-ascend-triage/)）：

| 缺陷 | 门禁时的表现 | 实际危害 |
|---|---|---|
| ≥3 层整图精度缺陷 | 1 层 cos 0.999999 PASS | 3 层起 cos 掉到 0.82，16 层 0.63——**任何多层模型的整图编译数值都不可信** |
| reduction 融合 kernel 退化 | 不测 kernel 计时 | LN 融合 6.7→70 μs，E2E 加速比 1.378x → 0.691x（负加速） |
| select_algorithm 签名漂移 | 跑在热缓存上不触发 | 清缓存后 `tuned_mm` 路径必崩 `LoweringException` |

三天的性能数据全部作废。更麻烦的是时间线倒挂：数据已经进了分析报告，报告已经发出去给人看过——**坏数据被引用的链路比坏数据本身难清理得多**。

## 复盘：g12 为什么拦不住

逐项对着三类缺陷问"为什么门禁没接住"，答案收敛到三个盲区：

**盲区一：单层探针测不到多层缺陷。** g12 用 1 层模型是有历史原因的（快、稳定、足以拦截当时的已知缺陷）。但精度缺陷不是按层数均匀分布的——这次的缺陷恰恰只在 ≥3 层整图编译时暴露（跨 kernel 的运行时交互，层数越多越易触发）。**探针的深度决定了门禁的感知边界**：1 层门禁的世界里，3 层的病不存在。

**盲区二：只测对错，不测快慢。** 精度门禁天然只看 cos。但版本组合的劣化有一大类纯粹是性能的——kernel 退化 10 倍，数值一个 bit 都不错。性能劣化不会让你的训练崩掉，只会让你的加速比悄悄归零，这比崩溃更隐蔽。

**盲区三：门禁的执行状态 ≠ 真实使用状态。** 门禁跑在热缓存上（编译缓存已存在），而真实用户第一次跑模型是在冷缓存上。签名漂移这类缺陷只咬冷缓存——门禁和用户走的不是同一条路径，看到的世界当然不同。

三个盲区指向同一个设计缺陷：**门禁测的是"这个环境能不能过我的探针"，而不是"这个环境交给用户后会发生什么"。**

## g13：3 分钟、5 项

新一代门禁按"真实使用路径"重新设计，一键脚本，exit code 即结论：

| # | 检查项 | 抓什么 | 为什么是它 |
|---|---|---|---|
| 0 | 清缓存 | 保证测的是新组合的真实行为 | 缓存不感知环境变化，不清 = 测旧产物 |
| 1 | 环境自报 | 记录 torch/torch_npu/CANN 版本号 | 后续所有判定依赖版本锚点；也是"数据作废范围"的判定依据 |
| 2 | g12（1 层 cos） | 原有回归项，保留 | 快速拦截历史已知缺陷，别把旧防线拆了 |
| 3 | **3 层 + 16 层整图 cos** | 多层精度缺陷 | 3 层是本次实测的发病阈值；16 层验证规模扩展性，seq=512 覆盖长序列 |
| 4 | **LN 融合 kernel 计时** | reduction 融合退化 | 固定 shape（[64,768]）compile 计时，健康值 3.6~6.7 μs，≥50 μs 即退化——不用懂融合原理，看数字就行 |
| 5 | **清缓存编译冒烟** | 签名漂移等冷缓存路径 | 第 0 步清过缓存，任意一条 mm 路径编译即覆盖 |

设计取舍很明确：**每项都必须能在 1 分钟内跑完**（总预算 3 分钟），所以不上全模型回归、不上长训练——那是 g13 通过之后深度验证的事。门禁的职责是**尽快说不**，不是全面体检。

### 判定标准写死在脚本里

```text
1L / 3L / 16L cos > 0.999          否则 FAIL
LN kernel < 15 us                  健康值 3.6~6.7，退化 ≥50
exit code 0 = 可采数据             非零 = 停止采数
```

exit code 是给自动化用的（CI/脚本链），打印文本是给人看的——两种消费者都照顾。

## 版本组合判断表：门禁之外的沉淀

跑门禁的次数多了，把每个组合的判定结果积累成表，新环境来了先查表再跑门禁：

| CANN | torch_npu 构建 | 3 层精度 | LN kernel | 判定 |
|---|---|---|---|---|
| 9.1.0 | git1b64dad | PASS | 6.7 μs | 可用（旧基线） |
| 9.2.0 正式 | git54e365d | **FAIL 0.82** | 70 μs | **禁用** |
| 9.2.0-beta.2 | git14dc54e | PASS | 3.6 μs | 可用 |
| 9.2.0 正式 | git14dc54e | PASS | 4.8 μs | **推荐**（当前生产） |

这张表抓到一个反直觉的事实：**病灶不在 CANN 版本线，在 torch_npu 的某个特定自编译构建**——同一 triton-ascend 下换构建即愈，三个 CANN 版本线都无罪。没有门禁逐组合过筛，这个归因根本立不住（三个变量同时换，凭肉眼永远分不清谁带病）。

顺带沉淀两条环境管理纪律：

1. **自编译 wheel 无背书**。`pip show torch_npu` 的 `direct_url.json` 指向 `file:///root/...`（本地打包）的构建未经任何验证——优先官方 wheel，或从已验证环境整体打包（venv 打 tar，别单独找 whl）。
2. **"清缓存后崩"≠ 新 bug**。签名漂移的表象是"只有清缓存才崩"，容易误判成偶发——它其实是稳定复现的冷路径缺陷，一行补丁的事。

## 门禁设计的四条通用原则

这次复盘的产出不止一个脚本，是可以迁移到任何"环境/版本/依赖频繁变动"场景的原则：

1. **探针深度 ≥ 缺陷分布深度**。门禁只测 1 层，就只能拦截 1 层的病。探针覆盖范围要由"缺陷会在哪暴露"决定，而不是由"跑多快"单方面决定——本次教训是给 3/16 层各加了 20 秒。
2. **对错和快慢都要测**。精度门禁 + 关键 kernel 计时，两类缺陷两条探针。性能退化不报错、不崩溃，只能靠数字抓。
3. **门禁路径 = 用户路径**。冷缓存编译、首次执行、真实 shape——探针走过的路必须和用户将要走的路重合，否则门禁通过只是探针的自嗨。
4. **判定结果落表积累**。单次门禁回答"这个组合行不行"，积累成表回答"哪类组合容易带病"——后者才是真正的选型知识。
