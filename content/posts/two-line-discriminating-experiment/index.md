> **TL;DR**：融合 kernel 输出错，最难的从来不是"修"，是"归因"——嫌疑列表五六个，每个都能自圆其说。本文案例（RoPE 融合 kernel 系数交叉）卡了数周，最后实锤它的是**两行对照**：同一 kernel，喂 contiguous 输入 bitwise 正确、喂行主序输入全错。数学对、索引错，嫌疑列表瞬间清空。根因是融合器允许不相邻轴合并，重索引位置语义无法表达；修复是两行守卫（不相邻 → 不合并），已进上游 PR [#47232](https://gitcode.com/ascend/pytorch/pulls/47232)。

## 案情：RoPE 输出错，五个嫌疑

现象：Llama 图模式下 rotary embedding（RoPE）相关的融合 kernel 输出与 eager 不一致。嫌疑列表：

1. **数学错**——融合 kernel 里 rotate_half/neg/cat 的实现写错
2. **索引错**——数学对，但读写地址算错（layout/重排类）
3. **精度累积**——fp16 下的正常数值误差，恰好越界
4. **上游数据坏**——kernel 无辜，输入进来的就是错的
5. **竞态**——多核执行顺序问题

五条嫌疑各有道理、各有支持者。逐个排查都要写实验，实验排错最大的成本不是跑，是**每个实验都只能排除一个嫌疑**。

## 实锤：两行对照

最后起决定作用的是把"输入 layout"做成唯一变量：

```python
# 同一个编译产物 kernel，同一个测试框架，只换输入的内存排布
kernel(BNSD_contiguous_input)   # → bitwise 正确
kernel(mm_rowmajor_input)       # → 全错
```

两行结果同屏对照，结论一锤定音：

- **数学没错**——contiguous 输入下 bitwise 正确，如果 rotate_half 的公式写错，两种输入都该错；
- **不是精度累积**——bitwise 对错是离散的，不是"误差大小"问题；
- **不是上游数据坏**——同一份上游，只换输入排布结果就翻转，问题在 kernel 对输入的**解读**；
- **不是竞态**——结果可稳定复现，不是随机。

剩下唯一解释：**索引错**。kernel 内部按 contiguous 假设计算地址，而实际收到的数据是另一种排布——读错位置，系数交叉。

一个实验清空四个嫌疑。这就是最小对照实验的杠杆：**不是多跑，是让一次跑产生最大的区分度**。设计要点是单变量——两组输入除内存排布外完全相同（同数据、同 shape、同 kernel 产物），差异才能唯一归因。

## 根因解剖：can_merge_dims 的语义漏洞

顺着"索引按错误 layout 生成"往下挖，凶手在融合器的维度合并逻辑。

inductor 生成融合 kernel 时会做**维度合并**：把多维张量的多个轴折叠成一维循环索引，减少循环嵌套。合并的前提是轴**相邻**——`[B, S, H, D]` 里合并 `(H, D)` 没问题，因为内存里它们本来就连续。

漏洞在于：`can_merge_dims` 的判断允许了**不相邻轴**合并。比如把 `(B, D)` 合并——两者在内存里隔着一个 S 轴，合并后的"折叠索引"要靠一个重索引函数（reindex）映射回多维坐标。对相邻轴，这个映射是线性的、无损的；对不相邻轴，**折叠索引的位置语义根本无法表达原坐标**——部分输入排布下能碰巧算对，换个排布就交叉。

这解释了为什么 bug 这么难抓：**它依赖具体的输入排布和合并决策**——同一个模型，某些 batch/seq 组合下没事，换个 shape 就坏；重放单 kernel 时如果恰好喂了"碰巧能对"的输入，还会得出"kernel 没问题"的假阴性。排错数周不是因为问题深，是因为它**间歇显形**。

## 三路互证

定案前做了三个独立验证，互相咬合：

1. **对照实验**（上文两行）——行为层面：错与输入排布强相关；
2. **产物静态解剖**——对照可合并轴对，确认非相邻合并确实发生、reindex 映射在该排布下语义错误；
3. **修复即痊愈**——加守卫后同构造重跑，全模型 cos 从不能看恢复到 1.004152，且此前"间歇坏"的 shape 组合全部转绿。

第三路常被轻视，其实是必需的：**修了就好**证明的是相关性闭环——没有它，前两路只是"高置信度的故事"。

## 修复：两行守卫

```python
def can_merge_dims(a, b):
    if b - a != 1:      # 不相邻 → 拒绝合并
        return False
    ...
```

守卫的哲学值得记一笔：**不做聪明事，只拒绝危险事**。理论上可以为不相邻轴实现更复杂的重索引语义，但那是新特性；当下的正确动作是把语义漏洞堵死——合法范围内的合并（相邻轴）行为不变，非法合并直接退化为不合并（性能上少一次折叠机会，正确性上再无灰色地带）。

修复走的是上游 PR（[#47232](https://gitcode.com/ascend/pytorch/pulls/47232)），对应 issue #5209。本地环境在 PR 合并前用同样守卫顶住（详见修改清单管理，参考[环境门禁篇](https://mol9026.github.io/tech-blog/posts/env-gate-g13/)的重装恢复场景）。

## 方法论沉淀

1. **嫌疑列表越长，越要找"一刀分两半"的实验**。五六个嫌疑逐个排查是 O(n)；一个好对照是 O(log n)——按"数学 vs 索引"、"确定 vs 竞态"、"输入 vs kernel"这样的二分轴设计实验，每刀砍掉一半。
2. **bitwise 是最好的判据**。能设计出 bitwise 对照就不要用"误差大小"——对错分明，没有解读空间。精度类问题才退而求其次看 cos/误差分布。
3. **间歇性 bug 先怀疑"决策依赖"**。间歇显形通常不是随机，是某个编译期决策（合并、调度、tiling）在某些输入下走了不同分支。找到那个决策点，间歇就变必然。
4. **修复即痊愈是定案的最后一环**。行为证据 + 静态证据之外，必须有"修了就好"的相关性闭环，以及——别忘了红绿灯——**撤了就坏**的反向验证（本案修复进了[红绿灯协议](https://mol9026.github.io/tech-blog/posts/red-green-fix-isolation/)的必要性判定，rc1 全撤 NaN 复现）。
