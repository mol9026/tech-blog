> **TL;DR**：一个 Llama 构造的图模式精度排查项目，前后定位了四个根因、落了四个修复。全部生效、门禁全绿、PR 排队待提——之后做了修复隔离验证（红绿灯）：**只撤一个修复，重跑门禁，和全修复态基线对照**。结果：
> - **两个修复真有必要**（撤销后故障复现， PR 成立）；
> - **两个修复零贡献**：一个要防的"错误"在依赖库新版本里早已被修掉；另一个的历史证据（cos 0.158 的惨案）是**别的 bug 未修时期的测量污染**，它要防的缺陷根本不存在。
>
> 教训浓缩成一句话：**绿灯 ≠ 每个修复都有必要**。多根因同时修复后，全绿只能证明"合起来有效"，证明不了"每个都必要"。

## 背景：一排绿灯，三个 PR

项目背景不复杂：某 Llama 构造在 `torch.compile`（Triton 后端）下图模式输出与 eager 不一致，cos 一度低到不能看。排查持续数周，陆续定位四个根因（按发现顺序编号 rc1~rc4），对应四个修复：

| 修复 | 针对的机制 |
|---|---|
| rc1 | 融合器允许不相邻轴合并，kernel 索引按错误 layout 生成 → RoPE 系数交叉 |
| rc2 | 给 attention 算子注册 layout 约束，强制 contiguous |
| rc3 | 构造侧 fp32 常量（inv_freq）被量化，相位误差随位置放大 → 常量豁免 |
| rc4 | reduction 融合 kernel 读改写同一 buffer，并发交错 → 输出放大 ~300×、偶发 NaN |

四个修复全部在位后，回归门禁全绿，历史故障不再复现。按正常节奏，接下来就是逐个提 PR 收尾。

但这里有个当时没被认真对待的问题：**四个修复是"一起"变绿的，没有任何一个被单独验证过贡献。**

## 为什么绿灯不可信

多根因项目的绿灯有个天然盲区——它只能证明合取，证明不了析取式归因。具体到这个项目，有两类风险先后都应验了：

**风险一：历史证据是"污染"的。** rc2 的立项依据是一个相当吓人的数据：attention 算子被喂 strided 输入时 cos 掉到 **0.158**。但这个测量是在 rc1 尚未修复的时期做的——而 rc1 的索引错位缺陷**同样会**让输出崩坏。换句话说，0.158 这个数字里有多少是 strided 输入贡献的、多少是 rc1 的底噪，当时的证据链分不开。修好 rc1 之后，"strided 输入"可能本来就是无辜的。

**风险二：目标在漂移。** rc3 要防的是"fp32 常量被量化成 fp16，相位误差随位置线性放大"——这在当时的依赖版本上是有据可查的行为。但依赖库（transformers）在迭代，新版本的 rotary embedding 前向已经把 inv_freq cast 回 fp32 计算。修复要拦的那扇门，别人已经焊死了。

两个风险有一个共同的解法：**把要定案的修复单独撤掉，看天塌不塌。**

## 协议：五步红绿灯

| 步骤 | 动作 | 关键点 |
|---|---|---|
| 1. 建绿灯基线 | 全修复在位，跑回归门禁，记录 cos/确定性数值 | 基线必须落盘，后面对照用 |
| 2. 隔离撤销 | **只撤目标修复，其余全部保留** | 见下方铁律 |
| 3. 跑红灯 | 同一门禁，合成用例 + 真实模型**各跑一组** | 合成用例绿灯只证明方案有效，真实模型才证明必要性 |
| 4. 对照判定 | 红灯退化 → 修复必要；完全一致 → 不必要；部分退化 → 细分再验 | 见下方细则 |
| 5. verdict 落盘 | 结论、方法、环境核查、证据文件路径写成 JSON | **evidence 只增不删**——这是归因修正的证据链 |

判定细则里最容易省略、也最不能省的是**环境核查**：红灯复现不出历史错误时，先核对依赖版本和时间戳，排除"库升级顺手修好了"的可能，然后才有资格下"归因错误"的结论。

### 三条铁律（每条都是学费）

**铁律一：按清单枚举全部触点。** 一个修复往往不止一处代码。当时有一个"双保险"型修复：注册层 + 调用点两层。第一次红灯实验只撤了安装点，故障不复现，差点据此得出"不必要"的错误结论——复查发现第二层还兜着底。此后撤销前先对着修改清单（PATCHES.md）枚举触点，双保险必须两个都撤。

**铁律二：清编译缓存。** inductor 缓存**不感知 monkeypatch**——改了 Python 侧补丁，不清缓存读到的是旧产物，跑出来的是假绿灯。撤销后必须先清缓存再跑。

**铁律三：合成用例和真实模型都要跑。** 合成 strided 用例单独绿灯，只能证明"约束方案本身有效"，证明不了"没有它真实模型会坏"——必要性必须用全模型数据说话。

## 三个判定实例

**rc4（reduction in-place）：必要 ✅**

全部相关触点撤销 + 清缓存 → 门禁 cos=None（NaN），历史故障完整复现；恢复后 cos=1.000014 PASS。红绿两态数据进了 PR，已合并收敛（[#47261](https://gitcode.com/ascend/pytorch/pulls/47261)）。

**rc3（fp32 常量豁免）：不必要 ❌**

隔离验证：量化构造 vs fp32 构造对照，graph cos 1.004152 vs 1.004134——噪声级差异。环境核查确认依赖库新版已自动 cast fp32。**该"缺陷"在当前栈上不存在**，取消 PR，指纹库里对应条目加了显式标注：此指纹在修复态编译器上为噪声级，命中先跑对照再下结论。

**rc2（FA layout 约束）：不必要 ❌**

完全禁用该修复（rc1/rc4 保留）后：前向 strided 直调 cos=1.0、反向 grad cos=1.0、全模型 cos=1.004152 与基线一致——**这个算子实际支持 strided 输入**。进一步产物层取证：编译产物里没有插入任何拷贝、结果仍然正确，比"结果对"更硬。历史 cos 0.158 确认为 rc1 未修复期的测量污染。取消 PR，历史 bug 报告加"归因修正"段（保留原结论原文 + 修正说明，不改写历史）。

## 归因修正不是丢人的事

直觉上，"撤掉自己的修复、证明它没必要"像是白干。但算三笔账：

1. **错误 PR 的代价是长期的**。一个约束注册进编译器，之后所有相关代码都要绕着它走；它拦住的是一个不存在的 bug，真正的 bug 检测信号却被它稀释。
2. **归因修正直接喂肥了指纹库**。指纹库的用法是"故障特征 → 查表 → 验证实验"，rc2/rc3 这类"特征像但其实是噪声/污染"的案例，恰好是表里最有价值的负样本——现在库里两条指纹都带着 ⚠ 警示标注，防止后来者重蹈覆辙。
3. **evidence 只增不删，链条可审计**。verdict JSON 落盘、历史报告保留原文加修正段——三个月后回看，能说清"当时为什么这么判、现在为什么改判"，而不是悄悄改口。

## 方法论沉淀

1. **多根因项目，定案前必须逐个隔离**。绿灯证明的是"合起来有效"；"每个都必要"只能靠红绿灯——单撤一个、跑门禁、对照基线。
2. **怀疑历史证据的出生日期**。任何"修复前测到的错误数据"，先问一句：测它的时候，其他根因修了吗？没修全的时期，所有数据都带着未知底噪。
3. **红灯不红，先查环境再翻案**。排除依赖升级、清缓存、触点枚举——把所有"假不红"的可能排掉，"归因错误"这个结论才成立。
4. **红绿两态数据跟着 PR 走**。必要修复的 PR 附上撤销即崩的数据，评审者不用信你的故事。
