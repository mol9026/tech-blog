> **TL;DR**：精度排查的四个高频问题，对应四个小工具：
> 1. **"修复之后还健康吗？"** → watchdog 门禁：四层检查一条命令，exit code 即结论；
> 2. **"哪里坏了？"** → doctor 金字塔：层级排除 → kernel 隔离 → buffer 溯源 → 指纹匹配，354 秒出诊断；
> 3. **"这个 kernel 单独跑对不对？"** → 隔离器：capture-replay，真实 buffer 任意次重放；
> 4. **"产物里有没有危险的内存复用？"** → 审计员：纯静态扫描，秒级，不用跑模型。
>
> 设计主线的两课：**工具按"回答一个问题"切分，不按流水线步骤切分**；**工具自己也要过红灯**——没拦截过真实故障的门禁不可信。

## 为什么是四件而不是一件

一个"精度排查 IDE"听起来更酷，但我们拆成了四个独立工具。切分依据是**排查者实际会问的四个问题**，它们出现在不同时机、由不同人触发：

| 问题 | 触发时机 | 频率 | 工具 |
|---|---|---|---|
| 修复之后还健康吗 | 每次改完代码、每次环境变动 | 每天多次 | watchdog |
| 哪里坏了 | 出了新问题 | 偶发 | doctor |
| 这个 kernel 单独对不对 | 定位深水区 | 高频（一次排查几十次） | 隔离器 |
| 产物里有没有危险模式 | 编译完顺手跑 | 每次编译 | 审计员 |

一体化工具会把四个问题绑进一条流水线——查个"健康吗"也要走完诊断全流程。拆开后，watchdog 可以进 CI 每夜跑，审计员可以挂在编译脚本末尾，隔离器可以单独喂给定位深水区。**工具的边界 = 问题的边界。**

## 1. watchdog：把"还健康吗"变成 exit code

背景很具体：四个修复散落在 site-packages 的 monkeypatch 里，**任何一次 torch_npu/triton-ascend 升级都可能悄悄冲掉它们**。"精度还达标吗"必须是一条命令能回答的问题。

四层门禁：

| 层 | 抓什么 | 判据 |
|---|---|---|
| G1 单层精度 | 索引错位类（快速信号） | 1 层构造 cos > 0.999 |
| G2 执行确定性 | 并发竞争类 | 同模型 10 次执行 bitwise 一致 |
| G3 端到端 | 构造侧语义 | 16 层构造 cos > 0.999 |
| G4 真实权重单层 | **编译器侧回归主门禁** | from_pretrained 真权重 cos > 0.999 |

exit code 三态：0=通过、1=精度失败、2=基础设施错误——给 CI 消费；JSON 报告带逐门禁数值——给人消费、可直接作 PR 证据。

**watchdog 的红灯自验有个决定性发现**：全回退态跑 G3（16 层端到端），**PASS，与绿灯逐位一致**——历史故障 0.657 主要由构造侧缺陷贡献，构造语义修正后这条路径根本不经过编译器的坏行为。换句话说，**门禁测错了主战场**。补救是加 G4（真实权重单层）——历史 0.9177 恰好是编译器侧缺陷的显形场。修正后完整回退态 G4 抓到 cos=None（NaN），exit=1，门禁闭环。

这一课超出 watchdog 本身：**门禁的探针路径必须和故障的真实显形路径重合**，否则绿灯只是探针的自嗨——和环境门禁 g13 的"门禁路径=用户路径"原则（[前文](https://mol9026.github.io/tech-blog/posts/env-gate-g13/)）同源。

## 2. doctor：金字塔式分层排除

输入"图模式输出不对"的模型，输出"哪一层、哪个 kernel、像哪类已知缺陷、怎么验证"。

| 层 | 干什么 | 耗时 |
|---|---|---|
| L1 层级排除 | 整体 cos + 两次执行确定性；健康即短路 | ~23s |
| L2 kernel 隔离 | 探针注入真实执行，逐站点重放 3 次 | ~20s（有产物时） |
| L3 逐 buffer 溯源 | data_ptr 同址改写检测 | ~2s |
| L4 特征指纹 | 误差按位置分布分析 | ~2s |

设计核心是**短路和顺序**：L1 健康 23 秒退出（穿刺普查时这是生死效率）；不健康才逐层下钻，每层产出直接是下一层的输入。L4 的产出直接对接[指纹库](https://mol9026.github.io/tech-blog/posts/npu-precision-fingerprints/)——匹配到指纹就打印"假设 + 下一步实验"，诊断报告落地成动作。

红灯自验同样过硬：全回退态 354 秒（含 5.5 分钟真实编译）自动给出"L2 site 12 重放不确定 → RACE；前 1/4 误差 inf 后 1/4 NaN → 数值爆炸；匹配并发竞争类"——人工当时花了数周走完的链路，自动化后六分钟。

## 3. 隔离器：capture-replay 消掉手工脚手架

定位深水区最高频的动作是"把单个 kernel 抽出来对不对"。手工做一遍要：读懂产物 Runner.call → 找调用点 → 从注释还原 buffer 语义 → 手工造输入 → 处理 stream → 写对拍。半小时起步，且**易错**——本项目两次重大误导都来自手工脚手架传参错序。

capture-replay 架构把整个循环工具化：

```text
list     列出产物全部 kernel 调用点（形状+源节点注释）——30 秒看懂整图结构
capture  注入探针，真实模型跑一遍，抓每个调用点的 pre/post buffer（含仪器自检）
test     任意 kernel 用真实输入重放 N 次：
         N 次间 bitwise 不一致   → RACE（并发竞争指纹）
         一致但 ≠ 捕获 post      → REPLAY-MISMATCH（输入状态/layout 依赖）
         全一致                  → KERNEL OK（错误在链路组合，转 L3）
```

三种结果直接映射三类嫌疑——工具输出即[指纹](https://mol9026.github.io/tech-blog/posts/npu-precision-fingerprints/)的输入。手工 30 分钟 → 秒级，且消掉了"脚手架本身是错的"这类最阴险的变量。它也是[两行代码实锤](https://mol9026.github.io/tech-blog/posts/two-line-discriminating-experiment/)那类对照实验的载体——喂不同排布输入重放，就是一条命令的事。

## 4. 审计员：秒级静态预检

前三个都要跑模型，第四个不用——纯静态分析产物源码，扫危险内存复用模式：

| 规则 | 风险 |
|---|---|
| reduction kernel 声明 mutated 参数（in-place 归约） | high——并发竞争核心指纹 |
| reduction 的输入来自 `# reuse` 复用 | high |
| 同一符号既输入又被就地改写 | high |
| 复用前面写过的 buffer | medium |

价值在**排序**：编译完先扫一遍，高风险模式直接决定诊断优先级。红色产物（回退态）秒级扫出 `reduction+inplace: mutated ['in_out_ptr0']`——正是后来修进 PR [#47261](https://gitcode.com/ascend/pytorch/pulls/47261) 的那条根因。绿色产物 0 alerts。红绿对照模式还能定位"修复前后产物差在哪"。

## 工具的可信度怎么建立

四个工具上线前都过了同一道关：**红灯自验**——故意回退修复、清缓存、真实编译，验证工具真的能拦截。watchdog 的红灯还顺带揪出了两个重大问题（G3 测错主战场；回退不完整导致的假阴性——修复点有两层只撤了一层）。三个纪律：

1. **绿灯只证明工具能通过，红灯才证明工具能拦截**。没有拦截过真实故障的门禁，可信度为零。
2. **红灯要真编译**。清缓存后 340 秒的全量编译是红灯可信度的成本——缓存命中态的红灯测的是旧产物。
3. **工具的盲区要写进文档**。watchdog 已知边界四条（缓存不感知 monkeypatch、非确定性缺陷需重复采样等）——用户知道边界，才不会把"工具没抓到"误读成"没有问题"。

## 方法论沉淀

1. **工具按问题切分，不按步骤切分**——四个问题四个工具，各自独立可用，组合成链。
2. **exit code 是工具的 API**。给人看的是报告，给机器看的是退出码——两者都设计好，工具才能进 CI。
3. **探针路径 = 故障显形路径**，门禁才有效（G3→G4 的教训）。
4. **自动化前先看手工在重复什么**。四件套没有一个是从零设计的——全是把排查中最高频、最易错的手工动作固化：跑门禁、分层排除、单 kernel 重放、扫复用模式。**工具是流程的化石。**
